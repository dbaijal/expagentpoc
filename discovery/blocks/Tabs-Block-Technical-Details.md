# Tabs Block — Technical Details & UE Authoring Contract

**Block Name:** Tab List (controller block) + Tab Panel (section variant)
**Maps To:** Tabs, Tab Container (AEM 6.4)
**Pattern:** Section-Based — each tab panel is a full OOTB section (not a child item inside a block)

**Reference Implementation:** https://github.com/adobe-rnd/aem-boilerplate-xwalk/pull/69

---

## 1. Architecture Overview

### 1.1 How Tabs Work in EDS (xWalk)

Tabs in EDS use a **section-based pattern**. This is fundamentally different from a container block with child items.

**Two components work together:**

| Component | What It Is | What It Does |
|---|---|---|
| **Tab List** | A block placed inside a regular section | The "controller" — its JS discovers tab panel sections, generates horizontal tab buttons, and manages show/hide behavior |
| **Tab Panel** | A section variant (same OOTB section with an extra `tab-label` metadata field) | The "content" — holds any blocks (cards, tables, video, etc.) and provides the tab label |

**Why this pattern:** The PDF requires tab panels to support Cards, Tables, Columns, Videos, Product Lists, and Images inside them. In EDS, only **sections** can hold blocks. Block child items can only hold field values (text, richtext). Therefore, each tab panel must be a section.

### 1.2 Page Structure

```
┌─ Regular Section ────────────────────────┐
│  [Tab List block]  ← controller           │
│  (generates tab buttons at delivery)      │
└───────────────────────────────────────────┘
┌─ Tab Panel Section (tab-label: "Tab 1") ─┐
│  [Any blocks — cards, table, video, etc.] │  ← first tab content
└───────────────────────────────────────────┘
┌─ Tab Panel Section (tab-label: "Tab 2") ─┐
│  [Any blocks]                             │  ← second tab content
└───────────────────────────────────────────┘
┌─ Tab Panel Section (tab-label: "Tab 3") ─┐
│  [Any blocks]                             │  ← third tab content
└───────────────────────────────────────────┘
┌─ Regular Section (no tab-label) ─────────┐
│  [Other page content]                     │  ← tabs group ends here
└───────────────────────────────────────────┘
```

**At authoring time:** Author sees vertical sections stacked on the page — nothing looks like tabs yet.

**At delivery time:** Tab List block JS transforms this into a tabbed interface — generates horizontal tab buttons, hides all panels except the active one, manages click/keyboard navigation.

### 1.3 How Tab List Block Discovers Tab Panels

The Tab List block JS uses **DOM sibling walking** — no explicit references or IDs needed:

```
Tab List block JS runs:
  1. Find the section containing the Tab List block
  2. Walk forward to the next sibling section
  3. Does it have data-tab-label? → YES → collect as tab panel
  4. Walk to next sibling section
  5. Does it have data-tab-label? → YES → collect as tab panel
  6. Walk to next sibling section
  7. Does it have data-tab-label? → NO → STOP collecting
  8. Generate <button> for each collected panel using its tab-label
  9. Show first panel, hide the rest
```

No configuration, no IDs, no references. The relationship is **positional** — consecutive sections with `tab-label` after the Tab List block become tab panels.

## 2. UE Authoring Contract

### 2.1 AEM Resources

**Tab List (controller block):**

| Property | Value |
|---|---|
| Resource Type | `core/franklin/components/block/v1/block` |
| Block Name | `Tab List` |
| Model ID | `tab-list` |
| Block Type | Simple block (no children — its content is generated by JS) |
| JCR Path | `/content/<project>/<path>/jcr:content/root/<section>/tab-list` |

**Tab Panel (section variant):**

| Property | Value |
|---|---|
| Resource Type | `core/franklin/components/section/v1/section` |
| Name | `Tab Panel` |
| Model ID | `tab-panel` |
| Filter | `tab-panel` (restricted — only allows blocks listed in PDF) |
| JCR Path | `/content/<project>/<path>/jcr:content/root/section_N` |

**Tab Panel is the same OOTB section component** — not a new resource type. The only difference from a regular section is:
- It uses the `tab-panel` model (which has a `tab-label` field)
- It uses the `tab-panel` filter (which restricts allowed blocks)
- It has `tab-label` metadata that the Tab List JS reads

### 2.2 Editable Properties in Universal Editor

**Tab List block properties panel:**

| JCR Property | UE Properties Panel | Field Type | Editable? | Notes |
|---|---|---|---|---|
| `classes_showAll` | Show All? | boolean (toggle) | Yes — Optional | When enabled, prepends a "Show All" button that displays all panels at once |
| `classes` | Style Variant | select | Yes — Optional | Options: default, classic-workflow |

**Tab Panel section properties panel:**

| JCR Property | UE Properties Panel | Field Type | Editable? | Notes |
|---|---|---|---|---|
| `tab-label` | Tab Label | text | Yes — Required | The text shown on the tab button. Pre-filled with "Tab" — author changes to meaningful label. |

**Inside the Tab Panel section:** Author adds any allowed blocks (cards, table, columns, video, product list, image, text, title) — these are the tab's content. Authored the same way as adding blocks to any regular section.

### 2.3 How Author Creates Tabs in Universal Editor

```
STEP 1: Author adds a regular Section
        Author drops a "Tab List" block inside it
        Optionally toggles "Show All?" and selects style variant

STEP 2: Author adds a "Tab Panel" from the section palette
        (appears alongside "Section" in the palette — separate option)
        Tab Label auto-fills with "Tab"
        Author changes it to "Products"
        Author drops Cards block inside this Tab Panel section
        (authors content exactly like any regular section)

STEP 3: Author adds another "Tab Panel"
        Changes Tab Label to "Specifications"
        Drops Table block inside

STEP 4: Author adds another "Tab Panel"
        Changes Tab Label to "Videos"
        Drops Video block inside

STEP 5: Author adds a regular "Section" for next page content
        (no tab-label → tabs group ends here)

DONE — author has created a 3-tab interface.
No explicit wiring needed. Tab List JS discovers panels by position.
```

**UE Section Palette shows two options:**

```
Section palette:
├── Section          ← regular OOTB section (for normal page content)
└── Tab Panel        ← section variant (for tab content — has tab-label field)
```

## 3. Component Model Definition (Field-Level)

### 3.1 Tab List Block Model

| Field | Component | Label | Required | Default | Validation | Authored / Derived |
|---|---|---|---|---|---|---|
| `classes_showAll` | boolean | Show All? | No | false | -- | Authored |
| `classes` | select | Style Variant | No | "" (default) | Options: default, classic-workflow | Authored |

**Note on `classes_showAll` naming:** The `classes_` prefix is an xWalk convention. When `classes_showAll` is set to `true`, it adds the CSS class `showall` to the block wrapper. The Tab List JS checks `block.classList.contains('showall')` to decide whether to add the "Show All" button.

### 3.2 Tab Panel Section Model

| Field | Component | Label | Required | Default | Validation | Authored / Derived |
|---|---|---|---|---|---|---|
| `tab-label` | text | Tab Label | Yes | "Tab" | Must not be empty — this becomes the tab button text | Authored |

**This is the entire model.** One field. The section content (blocks inside) is authored directly — not via fields.

### 3.3 Derived / JS-Generated Elements

| Element | Source | How Generated |
|---|---|---|
| Tab buttons (`<button role="tab">`) | `tab-label` from each Tab Panel section | Tab List JS reads labels from sibling sections, generates buttons |
| Active tab state | First tab panel | JS sets first panel visible, rest hidden by default |
| ARIA attributes (`aria-controls`, `aria-selected`, `tabindex`) | Generated by JS | Proper accessibility wiring — keyboard navigation with arrow keys |
| "Show All" button | `classes_showAll` on Tab List block | JS prepends "All" button if `showall` class is present |
| Mobile accordion collapse | CSS media query + JS | On mobile, tabs collapse to accordion — CSS/JS handles this, no authoring change |

## 4. Governance — Allowed Blocks Inside Tab Panels

### 4.1 Tab Panel Filter (Restricted)

Tab Panels use a **dedicated filter** that restricts allowed blocks to only those listed in the PDF:

```json
{
  "id": "tab-panel",
  "components": [
    "cards",
    "card",
    "table",
    "table-row",
    "columns",
    "video",
    "product-list",
    "image",
    "text",
    "title"
  ]
}
```

**What authors CAN add inside a Tab Panel:**

| Allowed Block | Why |
|---|---|
| Cards (+ Card items) | PDF requirement |
| Table (+ Table Row items) | PDF requirement |
| Columns | PDF requirement |
| Video | PDF requirement |
| Product List | PDF requirement |
| Image | PDF requirement |
| Text (default content) | Basic text content in panels |
| Title (default content) | Headings in panels |

**What authors CANNOT add inside a Tab Panel:**

| Blocked | Why |
|---|---|
| Hero | Not meaningful inside a tab |
| Accordion | Nested collapsible inside tabs adds complexity |
| Tab List | Cannot nest tabs inside tabs |
| Form Container | Not listed in PDF requirements |
| Embed | Not listed in PDF requirements |
| Fragment | Not listed — if needed later, add to filter |
| Modal, Search, Quote | Not listed |

**If more blocks are needed later:** Add the block ID to the `tab-panel` filter's `components` array. No other changes needed.

### 4.2 Comparison: Regular Section vs Tab Panel

| Aspect | Regular Section | Tab Panel Section |
|---|---|---|
| Resource type | `section/v1/section` | `section/v1/section` **(same)** |
| Model | `section` (has `classes`/style) | `tab-panel` (has `tab-label`) |
| Filter | `section` (allows ALL blocks) | `tab-panel` (allows ONLY PDF-listed blocks) |
| UE palette name | "Section" | "Tab Panel" |
| Metadata | `classes` (style) | `tab-label` (tab button text) |
| HTML output | `<div class="section">` | `<div class="section" data-tab-label="...">` |
| Tab List JS recognizes? | No | **Yes** (has `data-tab-label`) |

### 4.3 Tab List Block Governance

| Rule | Tab List Block |
|---|---|
| **Allowed in sections** | Yes — listed in section-level block filter |
| **Allowed on all page types** | Yes |
| **Is it a container** | **No** — it has no children. Its content (tab buttons) is generated by JS. |
| **Standalone** | Yes — author drops it into a section |
| **Typical placement** | Inside a section immediately before the Tab Panel sections |
| **Max instances per page** | Multiple tab groups can exist on one page (each Tab List block creates an independent tab group) |

## 6. Tab List Block JS — Implementation Logic

### 6.1 Core Logic

```
decorate(block):

  1. Find the section containing the Tab List block
     section = block.closest('.section')

  2. Walk forward through sibling sections to collect tab panels
     nextSection = section.nextElementSibling
     while nextSection has data-tab-label:
       collect [tabLabel, nextSection]
       nextSection = nextSection.nextElementSibling

  3. Generate tab buttons
     Create <ul role="tablist">
     For each collected panel:
       Create <button role="tab" aria-controls="panel-N">tabLabel</button>

  4. If "showall" class present:
     Prepend "All" button with aria-controls pointing to all panel IDs

  5. Wire up panels
     For each collected section:
       Set role="tabpanel"
       Set id="panel-N"
       Set aria-labelledby="tab-N"
       Set hidden (except first panel)

  6. Set first tab as active
     First button: aria-selected="true"
     First panel: visible (no hidden attribute)

  7. Add click handler
     On tab button click → hide all panels → show selected panel

  8. Add keyboard handler
     Arrow Left/Right → cycle through tabs
     Home/End → jump to first/last tab

  9. Replace block content
     block.replaceChildren(tabList)
```

### 6.2 Mobile Behavior

Per PDF: "On mobile devices, the tabbed interface will collapse into an accordion layout."

This is handled in CSS + JS:
- **CSS media query** detects mobile viewport
- **Tab buttons** transform from horizontal row to vertical accordion headers
- **Panels** behave as collapsible sections (expand/collapse on tap)
- **No authoring change** — same content, responsive rendering

## 7. Nested Authoring Strategy

### Classification: Section-Based (Unique Pattern)

| Pattern | Applies? | Reason |
|---|---|---|
| Flattened block | No | Tabs have multiple panels with different content each. |
| Parent-child container | No | EDS block child items can only hold field values (text, richtext). Tab panels need to hold full blocks (cards, tables, video). |
| Reference-based (fragment) | No | Would require creating separate fragment pages for each tab — unnecessary overhead. |
| **Section-based** | **Yes** | Each tab panel is a full OOTB section that can hold any blocks. Tab List block JS discovers panels by walking sibling sections. This is the only pattern that supports blocks inside tab panels without fragments. |

### Why Not the Accordion Pattern (Container + fragmentPath)?

For accordion, we used a container block with child items that have either richtext or a fragment reference. For tabs, the section-based approach is better because:

| Concern | Accordion Pattern (container + fragmentPath) | Section-Based Pattern |
|---|---|---|
| Blocks inside panels | Requires fragment pages — author creates separate page per tab | **Direct** — author adds blocks into the Tab Panel section normally |
| Author overhead | Must create + manage fragment pages | **None** — content is on the same page |
| Content is on the same page | No — fragment content lives elsewhere | **Yes** — all content is on the page |
| Editing experience | Must navigate to fragment pages to edit tab content | **Direct** — click the section, edit inline |
| UE preview | Fragment content may not preview inline | **Full preview** — content is in the section |

The section-based pattern is the recommended approach for tabs because the PDF explicitly requires blocks inside panels, and authoring is significantly simpler without fragment indirection.

## 9. Key Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Tab panel implementation | **Section-based** (not container child items) | PDF requires blocks inside panels — only sections can hold blocks in EDS |
| Tab panel as separate palette entry | **Yes** — "Tab Panel" appears alongside "Section" | Clearer for authors than adding tab-label field to regular section model |
| Tab panel filter | **Restricted** — only PDF-listed blocks | Prevents authors from adding inappropriate blocks (Hero, Accordion, nested tabs) |
| Tab List block content | **JS-generated** (no authored content) | Tab buttons are generated from sibling section tab-labels — no manual button authoring |
| Panel discovery | **Positional** (sibling section walking) | No explicit IDs or references needed — consecutive sections with tab-label are collected |
| Mobile behavior | **Accordion collapse** (CSS + JS) | Per PDF requirement — responsive, no authoring change |
| Multiple tab groups per page | **Supported** | Each Tab List block creates an independent group from its following Tab Panel sections |
| "Show All" option | **Boolean on Tab List block** | Per reference PR — adds an "All" button that shows every panel simultaneously |
